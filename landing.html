How it works

From test run to release decision
in four steps.

No agents to install. No config changes in your project. Point Pathlight at it and run.

01
Configure your project
Set your project root and Playwright config path on the config page. Pathlight reads your tests — it never modifies them.
02
Import or derive journeys
Upload a CSV of user journeys, or connect JIRA and let AI derive them from your user stories. Lock the manifest when satisfied.
03
Run your tests
Click Start run. Pathlight spawns Playwright with an injected reporter. Fishbone branches animate live as results arrive over SSE.
04
Read your verdict
GO · HOLD · BLOCKED. Computed from journey priority, business rule severity, and jurisdiction. A static HTML report publishes automatically.
Features

Everything tests are missing.

Pathlight thinks in user flows, not test files. Every feature reinforces that distinction.

🦴
Live fishbone visualisation
Journeys as bones, results as colour. Green, red, amber, and blocked states update in real time as Playwright runs.
🧠
AI journey derivation
Connect JIRA. Claude reads your user stories and derives happy paths, unhappy paths, edge cases, and boundary conditions automatically.
🗺️
Semantic test mapping
Point Pathlight at your test directory. It maps spec files to manifest journeys — no tagging required beyond a bracketed ID in the title.
⚖️
Business rule severity
Tag journeys with critical, high, medium, or low severity rules. A failing critical rule blocks the release regardless of overall pass rate.
🌏
Jurisdiction-aware risk
Business rules carry NZ, AU, or global jurisdiction. Risk statements reference the Privacy Act 2020 (NZ) or Privacy Act 1988 (AU) where relevant.
⌨️
CLI quality gates
Run pathlight gate in CI. Exit code 0 on pass, 1 on fail. Three-line GitHub Actions integration.
🔌
Provider-agnostic AI
Claude, OpenAI, Gemini, or local Ollama. Swap providers via config — zero code changes. Offline-capable for government and healthcare teams.
🐛
JIRA bug lifecycle
Create bugs from the evidence panel. Auto-create after consecutive failures. Pathlight comments when the journey passes again.
📋
Compliance audit trail
Every business rule, its severity, jurisdiction, and whether the journey verifying it passed. Timestamped. Linked to a run ID.
Release verdict

Not a pass rate.
A release decision.

Pathlight computes GO · HOLD · BLOCKED from journey priority, business rule severity, untested critical paths, and jurisdiction. It's what your CTO needs — not a spreadsheet of green ticks.

✓
GO
All critical journeys passed. Minor gaps documented.
⚠
HOLD
High-priority journeys failing. Core flows at risk.
✗
BLOCKED
Critical rule untested or failed. Legal or core product risk.

CLI

A CI citizen from day one.

The Pathlight CLI speaks to your running server. Quality gates, journey lists, gap reports, AI derivation — all from the terminal.

$ pathlight journeys
E2E-001 Waitlist form renders correctly passed happy
E2E-013 OAuth token refresh with expired session failed unhappy ← critical rule
E2E-020 Stripe checkout renders payment fields running happy

$ pathlight gaps
E2E-031 Password reset via email link untested
E2E-032 Account deletion with active subscription untested

$ pathlight gate --min-pass-rate=90 --no-critical-failures
⚠ HOLD — pass rate 87%, 1 high-priority failure
$ echo $?
1

$ pathlight query "which journeys failed in the last 3 runs"
E2E-013 failed in all 3 of the last runs.
E2E-015 failed once (run_20260531_003).
